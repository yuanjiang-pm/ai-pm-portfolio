## 四个我留下来的判断

写完这些，留下的就是这四条。每条都写了依据和代码，可以点进去看，也欢迎拿你自己的经验来讨论。

### 一、RAG 评估得分家看，混在一起就不知道问题在哪一跳

RAG 是个两阶段流水线：`Query → 检索 → Top-K 文档 → 生成 → 回答`。包括我在内，很多人一开始只看最终回答质量，这是瞎子摸象。

两个阶段的目标不同，评估方法也得跟着分家：

| 阶段 | 评估什么 | 怎么评估 |
|---|---|---|
| 检索 | 文档相关性排序 | IR 指标（Recall@K、Precision@K、MRR） |
| 生成 | 回答质量 | LLM-as-Judge（Faithfulness、Completeness、Relevance） |

我在 [D6](01-ai-evals/06-rag-eval-and-tooling.md) 里给了一个 2×2 诊断矩阵，用它可以直接定位瓶颈：

| | 生成好 | 生成差 |
|---|---|---|
| **检索好** | 健康 | 问题在 Prompt / 模型 |
| **检索差** | 检索没找到，但模型"编"出来了 ← 最危险 | 两边都有问题 |

左下角那格最危险：检索其实没找到，模型却凭参数知识编出一个看起来很像样的答案。只看最终答案的评估会把这种 case 判成通过，上线之后就是幻觉投诉。

→ 详细内容见 [01-ai-evals](01-ai-evals/)

### 二、Evals 的起点不是指标，是错误分析

我一开始也是从"该用什么指标"入手的，翻完 100 条真实 trace 才发现顺序反了。我见过团队花三个月搭评估体系，Dashboard 做得跟火箭控制台似的，上线后用户反馈跟没测过一样，我自己也走过这段弯路。问题出在起点：从"有什么现成指标"出发，而不是从"系统到底怎么失败"出发。

我用的路径是两步编码法（[D2](01-ai-evals/02-error-analysis.md)）：

1. **开放编码**：找 100 条真实 trace，逐条写观察笔记。不预判，不分类，不打分
2. **轴心编码**：把相似失败归类统计，直到理论饱和（连续 20 到 30 条没出现新模式）

还有一条我自己踩出来的经验：先找第一个失败。失败经常是链式的，上游错了下游跟着崩。只看最终输出，你会把锅全扣在生成模型头上，但 trace 可能显示问题出在检索模块的 query 改写。

→ 详细内容见 [01-ai-evals](01-ai-evals/)

### 三、LLM-as-Judge 不是圣人，裁判也得被考核

让 AI 当裁判是现在最流行的评估方法，但它有系统性偏见：宽容、严厉、位置、长度。我的体会是，不校准的裁判给不出多少有效信息：通过率从 30% 涨到 50%，你分不清是产品真变好了，还是裁判这周心情好。

校准方法（[D4](01-ai-evals/04-judge-calibration.md)）：准备 50 条以上人工标注真值，跑一遍裁判，算 TPR（识别好回答的能力）和 TNR（识别坏回答的能力）。

- 老好人裁判：TPR 0.95 / TNR 0.4，坏回答基本全放过
- 杠精裁判：TPR 低 / TNR 高，反过来

拿到 TPR 和 TNR 之后还能反过来修正原始通过率，估算真实水平。

三类评估方式的成本结构（[D1](01-ai-evals/01-what-is-evals.md)，数量级估算，实际随模型和任务浮动）：

| 方式 | 单次成本 | 1000 条成本 | 速度 |
|---|---:|---:|---|
| 人工评估 | 2 元 | 2,000 元 | 天级 |
| LLM-as-Judge | 0.1 元 | 100 元 | 小时级 |
| 代码 Eval | 0.01 元 | 10 元 | 分钟级 |

我现在的做法是分层组合：代码 Eval 覆盖 80% 常规检查并接入 CI，LLM-as-Judge 每晚批量跑全量，人工每天抽 5 到 10 条做高风险兜底。

→ 详细内容见 [01-ai-evals](01-ai-evals/)

### 四、模型的表现 = 模型 × 服务配置 × 输入卫生

这个判断不是从书上读来的，是亲手把一个 63.91M 参数的小模型从零训练到上线后，被十轮排障教出来的。

同一个模型权重，同一个问题，在 API 客户端里对答如流，在命令行里却开始复读——差的从来不是模型。拆开来是三个变量：

| 变量 | 出问题的样子 | 修复手段 |
|---|---|---|
| **输入卫生** | Agent 客户端把真问题埋在 5 万字符模板里，模型直接胡说 | 代理层瘦身，只把干净短问题喂给模型 |
| **服务配置** | 推理模板与训练模板差一个空行，输出立刻劣化；贪心解码掉进确定性复读循环 | 模板逐字节对齐；温度 A/B 实测裁决（temp 0 复读率 95%，temp 0.7 归零） |
| **输出防护** | 小模型走进点头循环，一次回答刷屏 56 万字符 | max_tokens 熔断 + 复读修剪 + 流式管线重构 |

排障十轮，没有一轮出在模型或训练上——全在"客户端方言"与"模型能力边界"之间。这对 PM 的启示是：**线上"模型变笨了"的投诉，先别急着换模型，先把输入分布和服务配置查一遍。** 多数时候模型是无辜的。

→ 完整实录见 [07-minimind-training](07-minimind-training/)
