## 一、嘉宾背景与访谈主线

### 她的履历

Dianne Penn 的职业路径本身就很有戏剧性：

- **摩根大通**：高收益债券交易员（金融背景出身）
- **亚马逊**：参与构建 Alexa 的 AI 能力
- **Anthropic**：2023 年加入，是公司**第一位 technical product manager**。当时整个产品团队只有 5 名工程师，API 业务甚至只有 1 名工程师

此后她深度参与了从 **Claude 2 到 Fable** 的每一次模型发布，并参与孵化了 **Claude Code、MCP、Skills、computer use、tool use、reasoning** 等几乎所有核心产品能力。

### 访谈核心命题

整场对话围绕一个主线展开：

> **前沿模型的能力增长不会自动变成用户价值。** 中间需要产品把新能力变成可探索的体验，需要 evals 把模糊的用户抱怨变成研究团队能处理的失败类型，也需要人持续验证模型到底做对了什么。

这也是这期访谈对 AI 产品经理最有价值的地方——它不是讲"AI 多厉害"，而是讲**"模型到产品之间这段落差，由 PM 来填"**。

## 二、Anthropic 早期：从绝望感中找到身份

### 加入时的真实状态

2023 年 Dianne 加入时，Anthropic 的处境并不光鲜：

- 产品团队只有 5 名工程师，API 只有 1 名工程师
- 当时外界的主流叙事是 **"OpenAI 已经赢了"**
- 没有人会把 "Anthropic" 和 "coding" 放在同一句话里

### 转折案例 1：Golden Gate Claude（24 小时上线的实验）

这是 Anthropic 历史上很有代表性的一个时刻：

- 可解释性研究发现，模型内部存在与特定主题相关的 **feature（特征）**
- 团队把 **Golden Gate Bridge（金门大桥）的 feature 调高**后，Claude 几乎每个回答都会谈金门大桥——问意大利面食谱，它也会把面条的颜色联系到金门大桥的"国际橙"
- 研究、产品、工程、设计一起协作，**24 小时内**把这个体验做进了 Claude.ai 公开上线
- 虽然只触达了约 2,000 人，但证明了一个重要道理：

> **研究可以用轻量体验公开验证，产品不必等所有东西成熟才出手。**

### 转折案例 2：Opus 3 与 coding 赛道的识别

- 团队当时不到 200 人，训练、测试、推理、微调、预训练之间形成了共同目标
- 研究负责人和产品团队在假期里一起盯训练结果（在各自父母家里通过视频看到彼此的童年房间）——建立了跨团队的信任
- 关键洞察：Dianne 观察到用户开始用模型写**长格式代码**（不只是自动补全）
- 这个观察成为训练 Opus 3 时的差异化机会——从训练角度看是相对小的变化，但竞争上帮助极大，让 Anthropic 找到了早期开发者用户群

> **启示**：PM 对产品方向的贡献，往往不是来自宏大的市场分析，而是来自对用户真实使用轨迹的细致观察。

## 三、四个核心概念（本期最大价值）

### 概念 1："Evals are the new PRDs"（evals 是新的 PRD）

这是 Anthropic 团队内部的真实口号，也是全期最出圈的观点。

**含义**：在模型产品中，真正代表用户价值的，不再只是一份描述愿景的文档，而是**把用户痛点变成一组可以反复运行的测试**。

**完整工作循环（四步）：**

1. **读取真实用户轨迹**  
用户说"Claude hallucinated（幻觉了）"还不够。团队继续追问：模型当时有没有调用工具？调用了正确的工具吗？看了正确的文档却抓错了事实吗？
2. **判断失败类型**  
问题属于 tool use、搜索、知识整合，还是 alignment？只有把反馈还原成失败轨迹，研究人员才知道下一步该改什么。
3. **抽象成 eval set**  
真实案例：早期大量用户反馈"Claude 不会遵循指令"。团队追问具体场景、输入输出后发现——**约 80% 的问题其实是模型没有生成正确的 JSON**。于是整理出 30-40 个具体例子形成 eval set：每个样本包含 prompt、模型 response、期望的 golden answer。
4. **反复运行测试**  
每次新版本模型发布，重新运行这组测试，检查问题是否真的改善。

**Dianne 的定义：**

> 这是 PM 的 test-driven development——先写清"什么叫做对"，再推动模型向这个标准靠近。

**重要边界（避免误读）：** evals 不是 PRD 的全面替代品——

- **已知问题**：适合用 eval 快速描述和追踪
- **模型发布**：仍需要 PRD 来让产品、工程、法务、安全等利益相关者对齐
- **未验证的新方向**（如 computer use）：PRD 里的产品愿景仍然有用，因为团队要先探索"怎样为某一类用户创造连贯体验"

### 概念 2：Token maxing（把成本换成发现）

**原始出处**：来自 Gary Tan 的一个判断——

> 如果你现在愿意一年花 10 万美元购买模型 token，你就是在提前体验 2028 年普通人才会拥有的工作方式。

**Dianne 的解读**：她明确拒绝把 token maxing 简化为"多花钱多调用模型"。她关心的核心是 **token spend 换来的输出——即实验**：

- Anthropic 内部最有创造力、最擅长原型的人，往往会反复使用每个新研究模型，先把它摸清楚，再从"能用"走到"好用"，最后形成产品想法
- 模型变化很快时，不亲手使用技术，就很难写出可信的策略
- 类比：过去的 PM 要 "sweat the pixels"（打磨像素细节），今天要 **"sweat the tokens"**——关注模型在上下文、调用和输出上经历了什么

**配套机制：公共试用文化**

早期 Anthropic 有一个 Slack 频道，几乎全公司一起测试 Claude：

> 一个人先提出用法，其他人很快用不同变体验证，十来次请求后，某个新的使用场景可能就浮现出来。

**实验不是个人运动，公共试用让组织共同发现模型的能力边界。**

**给个人的实操建议：**

- 不要把 token maxing 简化成"多调用模型"，先确定目标是实验和发现
- 选一两个真实问题深入做，通常比同时试几十个工具更容易获得稳定收益

### 概念 3：Jagged edge（锯齿边缘）

**定义**：描述 **AI 能力的不均匀性**——模型可能在某一类复杂任务上表现惊人，却在另一个看似普通的任务上暴露粗糙边缘。

**具体案例（写作）：**

- 即使语言模型大量学习过优秀文本，用户仍能从固定套路里认出"AI 味道"
- 更反直觉的是：当模型在 agentic 能力、工具调用等方面进步后，**写作可能反而成为更明显的短板**——因为其他能力进步了，短板就被衬托得更突出

**应对方式：把关注点转向可验证性**

Dianne 没有把问题归结为"AI 写得不像人"，而是问：

> **谁在检查输出？谁在签字确认？谁承担发布结果？**

- 月度业务复盘的写作可以委托给 Claude，但**信息的验证、判断和最终签字不能一起委托出去**
- 这背后与 evals 是同一逻辑：AI 产品的工作不是追求每一次输出都可预测，而是把"什么算是好结果"说得足够清楚，用测试、复核和责任边界守住模型还没跨过去的边缘

### 概念 4：指数曲线内部的心态（Product overhang）

**技术背景**：原始 scaling law 论文里的"涌现能力图"——模型能力不是平滑上升，而是**不连续跳跃**。

- 这意味着安全更难：除非有 evals 和测试系统，否则能力跳跃发生了你也不知道
- Dianne 提出 **"product overhang"（产品欠账）和 "user overhang"（用户欠账）**：即使今天的模型，也还有大量未被探索的能力没被产品化、没被用户发现

**身处指数曲线内部的两条生存法则：**

1. **适应性（Adaptability）**：无法预测确切时刻，但可以训练面对新信息时调整决策的能力，而不是坚持原计划
2. **第一性原理推理**：不断问 "so what？"——这件事意味着什么？对今天的构建意味着什么？

她给团队的问题框架：

> **假设 Claude 8 来了。用户能做什么会改变？这对你今天如何构建意味着什么？**

## 四、她对 AI 产品经理角色的六个观点

### 1. 必须亲手交付

> 不能只停留在讨论 AI，要亲自用它、亲自交付。

具体做法：

- 为自己保留一到两个工作流，持续观察模型怎样变化，保持对模型能力的"理论心智"和对速度的感知
- 即使是经验丰富的 PM，新加入团队时也要从理解用户、阅读反馈、和客户交流、亲手构建开始

> 没有亲手做过，就很难判断一个 AI 产品的好坏，也很难理解团队遇到的真实限制。

### 2. PM 的核心价值是"找到正确的用户反馈和 evals"

> 对于我的团队，驱动用户价值的方法是弄清楚正确的用户反馈和 evals。

### 3. 用"未来问题"引导今天的构建

即用 Claude 8 的假设来倒推今天的产品决策（见上文）。

### 4. 产品与模型是共生关系

> 你需要前沿产品才能拥有前沿模型，才能让人们感受到前沿模型的魔力。

Opus 4.5 和 Claude Code 的关系是互相放大的：没有 Claude Code，Opus 4.5 不会有那个时刻；没有 Opus 4.5，Claude Code 的采用也不会加速。

### 5. AI 需要反驳用户

一个很反直觉但深刻的观点：

> Claude 的 constitution、alignment 和 safety 训练让产品更有趣，恰恰因为模型不会对所有想法都点头。**一个只会同意用户的助手不能真正改善判断，适时的 pushback 才像有用的同事。**

她自己的用法：面对需要个人判断的议题，**先形成自己的观点**，再让 Claude 作为 sparring partner（陪练）推动、质疑和完善。她还把《Crucial Conversations》的方法做成 skill，高难度沟通前让 Claude 检查：是否足够具体？是否应该更直接？是否遗漏了对方的反应？

### 6. 帮助不习惯 AI 的人

一个"不太鸡汤"的建议：

> 不要独自寻找完美用法。找一个已经对这项技术有兴趣的人，围绕自己真正关心的问题一起试。

共同发现比被迫打卡更可能带来乐趣。

## 五、Labs 的孵化哲学：「强坚持、弱承诺」

Dianne 负责的 Labs 团队有一套独特的孵化机制：

- **对主题强烈坚持，对具体原型保持较弱的承诺**
- 原型即使没有立即发布，只要帮助团队理解了未来一两代模型可能出现的机会，也有价值
- 某个想法现在做不成不代表永远不做，可能在一两次模型迭代后重新回来看
- 与传统创新部门的区别：**不把"实验失败"当成无效产出**
- 团队建设：需要能承受零到一不确定性的人，同时用小团队保持速度

**她观察到的优秀研究员共同素质：**

- 用第一性原理推理问题
- 对自己的研究领域足够着迷，能保持对训练细节的兴趣
- 敢于把目标想得很大
- **对方向保持执着，对实现路径保持松弛**——因为模型能力变化太快，原来的做法可能很快失效

## 六、核心观点速查表

| 观点 | 一句话概括 |
|-|-|
| 模型↔产品共生 | 前沿产品才能让前沿模型被感受到，两者互相放大 |
| Token maxing 的本质 | 不是多花钱，而是把成本换成实验和发现 |
| Evals 是新的 PRD | 把用户痛点变成可反复运行的测试 |
| 亲手使用不可替代 | PM 必须亲自用模型、亲自交付，才能保持判断力 |
| Jagged edge 应对 | 谁在检查、谁在签字，比谁来写更重要 |
| AI 需要反驳用户 | 只会同意的助手不能改善判断 |
| 适应性优先于预测 | 无法预测确切时刻，但可以训练面对新信息时的决策能力 |
| 公共试用 | 个人实验 + 公共分享 = 组织共同发现能力边界 |
| 强坚持弱承诺 | 对主题执着，对原型松弛，失败也是有效产出 |

## 七、对 AI 产品经理的落地启发

对照《AI 产品经理实操手册》，这期访谈提供了 Anthropic 一线实证：

1. **"Evals are the new PRDs"** → 正是手册"转变一：管评测"的一线版本。注意 Anthropic 的做法比手册更进一步：从真实用户轨迹里**反推失败类型**再抽象成 eval，而不是凭想象写测试用例
2. **"谁检查、谁签字"** → 正是手册中"人审门"设计的核心逻辑——委托写作但不委托判断
3. **"假设 Claude 8 来了"** → 可以作为写目标说明书（Objective Spec）时的标准提问模板
4. **公共试用文化** → 手册中的"混合团队监控"可以补充一个组织实践：建一个全团队的试用频道，让发现变成集体活动
5. **强坚持弱承诺** → 对 AI 原型的管理心态：不因单次失败否定方向，但也不过度承诺某个具体实现
