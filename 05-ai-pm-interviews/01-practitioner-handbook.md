# AI 产品经理实操手册

> 基于《No Priors × Satya Nadella（微软 CEO）》播客单集延伸：AI 产品经理的定位与落地方法。  
> 核心观点：AI 产品经理的交付物从「文档」变成了「系统」——你定义的不是功能，而是 agent 行为的「游戏规则」。

---

## 一、定位：你在 Nadella 蓝图中的角色

Nadella 那期聊的是**工程师角色的压缩**，但框架对 AI 产品经理恰恰有最直接的映射：

- **你是「超杠杆通才」（Hyper-Leveraged Generalist）**：AI 正在把通用型人才的杠杆放大到极致。PM 的本质就是通才——过去短板是执行带宽，现在 AI 把它抹平了。「定义正确的问题 + 编排 AI 把它做出来」就是 AI PM 的超级能力。
- **你正在成为「Agent 管理员」的人类侧负责人**：知识工作的默认形态是「agent 整夜替你干活」。工程侧的人搭 harness、写工具、调 loop；产品侧的你的主场是——定义 agent 要达成的目标、设定质量标准与验收标准、判断输出对不对。
- **「私有评测（private evals）可能是企业最大的 IP」**：谁定义评测标准，谁就掌握了产品的方向盘。这在传统产品里叫「验收标准」，在 AI 产品里被提升到了战略资产的高度。

### 三个核心转变

| 转变 | 从 | 到 |
|-|-|-|
| 转变一 | 管功能 | 管评测（Evals） |
| 转变二 | 管开发 | 管编排 |
| 转变三 | 管人 | 管「人 + agent」混合团队 |

---

## 二、转变一：从「管功能」到「管评测（Evals）」

**本质变化**：传统 PM 交付《需求文档》，AI PM 交付《评测体系》。你不再描述「系统应该做什么」，而是定义「什么算做对了」。

### 第 1 步：把每个产品需求拆成「可判对的基准」

传统 PRD 条目 → 转成 eval 用例：

```markdown
需求：AI 客服能识别用户情绪
↓ 转成 eval
输入：用户说「你们这个 bug 三天没修了，我很生气」
期望：agent 必须 ① 先道歉 ② 不辩解 ③ 给出修复时间预期
判定方式：rubric 打分（0-3 分，≥2 分通过）
```

### 第 2 步：建三张 eval 集

| 类型 | 内容 | 来源 |
|-|-|-|
| Golden Set（黄金集） | 100+ 条「必须答对」的典型输入 | 从用户反馈、客服记录里挑最有代表性的 |
| Edge Case（边界集） | 模糊、对抗、敏感输入 | 竞品翻车案例、安全团队、红队测试 |
| Regression（回归集） | 历史所有改坏过的用例 | 每次线上事故、每个用户投诉，都沉淀进来 |

### 第 3 步：定「发布门禁」——把 eval 变成上线的闸门

```markdown
模型/提示词/工作流任何改动 → 跑全量 eval
通过率 < 95%（按你业务定）→ 不许上线
新增 20 个线上失败案例 → 进 eval 集 → 修复 → 通过后才能发
```

### 第 4 步：选工具

- **Promptfoo**（免费开源，写 YAML 就能跑）——最快的起步方式
- **LangSmith / Langfuse**——需要追踪线上行为时用
- 成熟后再考虑 Braintrust 这类商业 eval 平台

### Eval 用例卡片模板（建 50 条就够启动）

```markdown
## Eval 用例 #001
- 场景：客服—情绪识别
- 输入：「你们这个 bug 三天没修了，我很生气」
- 期望行为：①先道歉 ②不辩解 ③给时间预期
- 判定：rubric 打分，≥2/3 通过
- 来源：2026-07 用户投诉 #8821
- 严重度：高（涉及品牌信任）
```

> **关键认知**：这一块是 AI PM 的「护城河」。Nadella 说的「私有评测是企业最大的 IP」，落到你身上就是——**你对「什么是好」的判断，正在变成公司最值钱的资产**。这也是最容易被 AI 工程师抢走的领地，你必须主动握在手里。

## 三、转变二：从「管开发」到「管编排」

**本质变化**：过去你写 PRD 让工程师实现；现在你写「目标说明书」，定义目标、约束、工具、质检点，让 agent 执行，你当**总导演**。

### 第 1 步：把 PRD 改写成「目标说明书（Objective Spec）」

```markdown
## 目标：做一份 2026 竞品 AI 功能盘点报告
- 目标输出：20 页报告，含表格对比、引用来源
- 成功标准：①信息日期 ≤30 天 ②每个观点有链接 ③结论可执行
- 边界：只分析国内主流 AI 产品，不含海外
- 安全规则：涉及财务数据的部分必须人工复核
- 质检点：第 5 步（数据收集完）和第 9 步（初稿完成）必须停下给我审
```

### 第 2 步：掌握「编排的三种粒度」

| 粒度 | 适用场景 | PM 要做的 |
|-|-|-|
| 单 agent 直跑 | 简单生成类（摘要、翻译） | 写好 prompt + eval 门禁 |
| 多 agent 流水线 | 有明确步骤的复杂任务 | 定义步骤拆分、每步的验收标准、步骤间的交接格式 |
| agent 团队 | 需要协作的长任务 | 定义角色分工（调研员/写作员/质检员）、共享上下文、冲突仲裁规则 |

### 第 3 步：设「人审门（Human Gate）」

- 低风险高频（如文案初稿）→ 全自动，抽检 10%
- 中风险（如客服回复）→ 关键节点人审
- 高风险（如合同、医疗、财务）→ 强制人工复核，agent 只做草稿

### 第 4 步：你的日常节奏变成「导演制」

```markdown
周一：分配本周任务包（目标说明书 + 工具 + eval 门禁）
周二~周四：agent 干活，你看监控面板（失败率、成本、卡点）
周五：跑 eval 回归，人审高风险输出，沉淀新 eval 用例
```

> **关键认知**：你最大的精力投入点在**定义任务包的边界和质检点**。边界定得清楚，agent 出错少；质检点放得对，出错了也兜得住。这一步决定了你是「指挥 AI」还是「被 AI 输出淹没」。

## 四、转变三：从「管人」到「管『人 + agent』混合团队」

**本质变化**：你的团队不再是「一堆工程师」，而是「几个核心人 + 一群 agent」。你要设计**谁做什么、什么时候信任 agent、什么时候必须找人**。

### 第 1 步：画一张「人机分工图」

对每条工作流，标注两个维度：**频率**（高频/低频）× **风险**（低/高）：

|  | 低风险 | 高风险 |
|-|-|-|
| **高频** | agent 全自动 + 抽检 | agent 初稿 + 强制人审（如客服） |
| **低频** | agent 直跑 + 抽查 | **人主导 + agent 辅助**（如战略决策） |

### 第 2 步：建立「信任分级」制度

```markdown
L1 全自动：结果直接可用（如格式化、翻译）
L2 需抽检：10% 人工复核（如文案初稿）
L3 需人审：关键节点必须人确认（如对外发布）
L4 只做建议：产出参考，人做决策（如方案建议）
```

### 第 3 步：给 agent 定「升级路径」——遇到什么情况必须停下来找人类

```markdown
触发升级的场景（任一命中即停止）：
- 检测到内容涉及 法律/医疗/财务 等敏感领域
- 请求次数超限（如重试 3 次仍失败）
- 用户表达强烈负面情绪（愤怒/威胁/投诉升级）
- 需要的权限 agent 没有（如访问用户隐私数据）
```

### 第 4 步：建「混合团队监控面板」

| 看板项 | 含义 | 你采取的动作 |
|-|-|-|
| 任务成功率 | agent 完成质量 | 失败率高 → 改 prompt / 加人审门 |
| Token 成本 | 每任务消耗 | 超预算 → 降粒度 / 换便宜模型 |
| 升级触发数 | 兜底机制生效次数 | 过多 → 说明边界定义有缺陷 |
| 人工干预率 | 人不得不介入的比例 | 太低 → 检查是否过度信任 agent |

### 第 5 步：组织动作也要带 agent

```markdown
OKR 示例：
KR1：客服回复 agent 化率从 30% → 70%（人工干预率 <15%）
KR2：eval 通过率 ≥95%，线上投诉下降 40%
KR3：单任务成本下降 50%（token 优化）
```

> **关键认知**：混合团队管理的本质是**「信任治理」**——你是在给 agent 做「入职培训、绩效考核、风险管控」。最强的 AI PM，是把 agent 管得像一支纪律严明的外包团队，而不是「散养一堆黑盒」。

---

## 五、一句话串起来（你的新工作流）

> **定义评测标准（管评测）→ 写成目标说明书（管编排）→ 授权并监控 agent（管混合团队）→ 人审高风险 + 沉淀新用例 → 回到评测体系（飞轮转起来）**

这套流程每次迭代一个产品功能就跑一圈，循环越快，你的「私有评测资产」越厚，你在公司的话语权越大。

## 六、附录：如何进入 AI 研发领域（Lex Fridman #490 嘉宾建议）

> 补充来源：Lex Fridman Podcast #490《State of AI in 2026》（2026 年 1 月），嘉宾 Nathan Lambert（AI2 后训练负责人，《The RLHF Book》作者）与 Sebastian Raschka（《从零构建大语言模型》作者），在 2:12:43 处专门讨论了给新人的入行建议。与上文「管评测」「管编排」的能力建设互为补充。

### Sebastian Raschka：从零实现一个模型（技术路径）

核心思想：**「最好的学习方式就是亲手从零构建」**。

1. **在自己的笔记本上从零写一个小 LLM**（从 GPT-2 规模写起）

   - 目标是「理解大语言模型里面到底有什么」，不是做个能用的产品
   - 亲手实现**预训练、注意力机制、微调**，然后会自然撞上真实世界的瓶颈：参数分片、KV 缓存实现细节、分布式系统
2. **验证技巧**：从 Hugging Face Transformers 加载预训练权重，跑在你自己的实现里——**如果输出一致，你的实现就是对的**（"代码不会撒谎，能跑通就是正确"）
3. **刻意练习与 AI 并存**：每天留约 2 小时完全不用 AI 纯手工练习，其余时间配合 AI。原因：调查显示资深工程师比初级工程师更依赖 AI 生成代码，因为「有效使用 AI」本身是需要经验积累的技能——从不经历自己写代码的挣扎，就永远到不了能正确判断 AI 输出的水平
4. **读书方法**：第一轮离线专注阅读，让内容沉淀；第二轮再借助 LLM 查细节（"使用 LLM 是第二遍的事，不是第一遍"）

### Nathan Lambert：从利基领域和评测切入（职业路径）

适合「没有算力资源的研究者」的出头路径：

1. **创建「能让前沿模型失败」的评测基准（eval）——零计算资源研究者最有影响力的路径。如果你的基准被 Claude 或 GPT 下一版在博客里引用，职业生涯就起飞了**（与本文档「管评测」一节完全同源：你在产品侧建私有评测资产，研究员用评测证明模型边界）
2. **找一个足够窄的利基领域深挖**：花几周真正搞懂一个狭窄话题，做到**全世界可能只有 2-3 个人在深度关注**，然后直接发邮件给那几个人

   - 真实案例：一个牛津学生主动联系他对「角色训练」（如何让模型变得幽默/讽刺/严肃）感兴趣，当时全球可能只有 2-3 个人在研究，他指导后论文已发表
3. **如果进了前沿实验室**：最有影响力的贡献往往不是「发明下一个 o1」，而是**找到更好的训练数据，或让团队实验跑快 5%**（"花哨的算法工作是最性感的想法，但大多数贡献是让数据更好，或让基础设施更好"）

### Lex 的补充

他喜欢一开始就用 LLM 搭出整个领域的宏观图景（「这个世界是什么样的」），但会刻意避免经由 LLM 跳进社交媒体或博客的「兔子洞」。

### 两条路径对照

| 嘉宾 | 路径 | 核心 | 对应本文档能力 |
|-|-|-|-|
| Sebastian Raschka | 技术路径 | 把地基打牢（懂原理） | 管评测的基础判断力 |
| Nathan Lambert | 职业路径 | 找准生态位（做贡献） | 管评测 / 管编排的落地策略 |

> 两条路径不冲突，可以先后都要：先用 Raschka 的方法打技术底子，再用 Lambert 的策略找自己的生态位。
