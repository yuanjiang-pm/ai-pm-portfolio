# D12：RAG架构

## 📖 今日主题

RAG不是微调，是"检索+生成"——让LLM用外部知识说话，而不是靠记忆编话

---

## 概念讲解

### 为什么需要RAG？

LLM有三个天生的硬伤，RAG就是冲着这三刀去的：

| 问题 | 表现 | RAG怎么解决 |
|-|-|-|
| 幻觉（Hallucination） | 编造不存在的事实，一本正经胡说八道 | 检索到真实文档作为依据，让模型"看着答案说话" |
| 知识过时（Staleness） | 训练数据截止后发生的事一概不知 | 向量数据库实时更新，无需重新训练模型 |
| 缺乏领域知识 | 通用知识还行，专业领域（法律、医疗、企业内部）一问三不知 | 灌入领域文档，检索相关片段作为上下文 |

🕯️ **核心认知**：RAG的本质是**把"记忆"外挂化**。LLM的参数里装的是训练时的"记忆"，但记忆会过时、会有遗漏。RAG给LLM配了一个随时可以查的"资料库"，让它从"凭记忆回答"变成"查资料回答"。

---

### RAG流程：四步走

```
用户查询 → 查询处理 → 文档检索 → 上下文整合 → 响应生成
```

#### Step 1：查询处理（Query Processing）

用户的原始查询不一定适合直接检索，可能需要处理：

- **查询改写（Query Rewriting）**：把口语化问题转成更适合检索的形式
- **查询分解（Query Decomposition）**：复杂问题拆成多个子查询
- **查询扩展（Query Expansion）**：补充同义词、相关术语
- **HyDE（Hypothetical Document Embedding）**：先让LLM生成假设性答案，再用这个答案去做检索（因为假设性答案的embedding更接近真实文档的embedding）

#### Step 2：文档检索（Document Retrieval）

这是RAG的核心环节，决定了"找到的资料对不对"。

**向量检索流程**：

1. 用Embedding Model将查询文本转为向量（query embedding）
2. 在向量数据库中做相似度搜索（通常是余弦相似度或点积）
3. 返回Top-K个最相似的文档片段（chunks）

**混合检索（Hybrid Search）**：

- **稠密检索（Dense Retrieval）**：基于向量相似度的语义搜索——理解"意思"
- **稀疏检索（Sparse Retrieval）**：基于关键词匹配（如BM25）——精确匹配"词汇"
- 混合两者效果更好，因为语义搜索可能漏掉精确术语，关键词搜索可能漏掉语义相关的表达

**重排序（Reranking）**：

- 初步检索后，用更精确的模型对Top-K结果重新排序
- NVIDIA NeMo Retriever Reranker就是做这个的
- 把最相关的片段排到前面，提高送入LLM的信息质量

#### Step 3：上下文整合（Context Integration）

把检索到的文档片段和用户查询拼在一起，构造给LLM的完整Prompt：

```
[系统指令] 你是一个助手，请基于以下参考资料回答问题...
[检索到的文档片段1]
[检索到的文档片段2]
...
[用户问题] xxx
```

**关键考量**：

- **Context Window限制**：LLM有上下文长度限制，检索回来的文档不能超
- **信息排序**：最相关的信息放在前面（Lost in the Middle效应——LLM对中间位置的信息注意力较低）
- **去重与压缩**：避免重复信息浪费token

#### Step 4：响应生成（Response Generation）

LLM基于增强后的Prompt生成回答。关键是让模型**忠实于检索到的上下文**，而不是自己编。

**降低幻觉的技巧**：

- Prompt中明确要求"仅基于提供的参考资料回答"
- 如果检索到的上下文不足以回答问题，让模型回答"我无法基于提供的信息回答"
- 使用Guardrails进行事实性检查

### 向量数据库：Embedding → 存储 → 搜索

这是RAG的基础设施，考试必考。

#### Embedding（嵌入）

**是什么**：把文本转换成高维数值向量，使得语义相近的文本在向量空间中距离近。

**过程**：

```
"什么是深度学习？" → Embedding Model → [0.12, -0.34, 0.56, ..., 0.78]  (通常768-4096维)
```

**关键特性**：

- 语义相似的文本 → 向量距离近
- 语义不同的文本 → 向量距离远
- 常用距离度量：余弦相似度（Cosine Similarity）、欧几里得距离（Euclidean Distance）、点积（Dot Product）

#### 向量存储与索引

**存储流程**：

1. 文档切分（Chunking）：把长文档切成合适大小的片段
2. Embedding：用Embedding Model将每个片段转为向量
3. 存入向量数据库：向量+原始文本+元数据

**索引结构**：

- **精确搜索（Exact Search）**：暴力计算所有向量距离，准但慢
- **近似最近邻搜索（ANN, Approximate Nearest Neighbor）**：用索引结构加速，牺牲少量精度换大幅提速

  - **IVF（Inverted File Index）**：先聚类再搜索
  - **HNSW（Hierarchical Navigable Small World）**：图结构索引，搜索快
  - **PQ（Product Quantization）**：向量压缩，省内存

**常见的向量数据库**：Milvus、FAISS、Pinecone、Weaviate、pgvector

#### 相似度搜索

```
用户查询 → Embedding → query_vector
在向量数据库中找与query_vector最相似的Top-K个向量
返回对应的原始文本片段
```

**GPU加速**：NVIDIA的cuVS库提供GPU加速的向量索引和搜索，显著提升大规模向量检索性能。

### RAG评估：三层拆解

RAG是"检索+生成"的双模块系统，评估必须拆到每个环节。

| 评估层 | 核心问题 | 关键指标 |
|-|-|-|
| 检索质量 | 找到的资料对不对、全不全 | Context Precision（精确率）、Context Recall（召回率）、MRR |
| 生成质量 | 有没有用找到的资料正确回答 | Faithfulness（忠实度）、Answer Relevance（答案相关性） |
| 端到端评估 | 整体好不好用 | 幻觉率、答案正确性、响应一致性 |

#### 检索层指标

- **Context Precision**：检索回来的文档中有多少是相关的（"找得准"）
- **Context Recall**：回答问题所需的信息有多少被检索到了（"找得全"）
- **MRR（Mean Reciprocal Rank）**：正确文档在排序中的位置——排得越靠前越好

#### 生成层指标

- **Faithfulness（忠实度）**：答案中的每个陈述是否都能在检索到的上下文中找到依据——这是防幻觉的核心指标
- **Answer Relevance（答案相关性）**：答案是否切题，有没有跑偏

📖 **关键区别**：Faithfulness vs 答案正确性

- Faithfulness高 = 答案忠于检索到的文档（但文档本身可能错）
- 答案正确 = 答案事实上正确
- 一个答案可以Faithful但Incorrect（忠于了错误的文档），也可以Correct但Unfaithful（答案对但不是从文档推导的）

#### 端到端指标

- **幻觉率** = 1 - Faithfulness
- **答案正确性**：与标准答案的匹配度（有标准答案用EM/F1，没有用LLM评分）
- **响应一致性**：相同问题多次回答的语义相似度

**评估框架**：

- **RAGAS**：最流行的RAG评估框架，提供参考无关的自动评估指标
- **ARES**：微调小模型做评估，更鲁棒
- **NVIDIA RAG Blueprint**也集成了RAGAS评估脚本

## 关键对比

### RAG vs 微调（Fine-tuning）

| 维度 | RAG | Fine-tuning |
|-|-|-|
| 核心机制 | 检索外部知识+LLM生成 | 更新模型权重 |
| 知识更新 | 实时（更新数据库即可） | 需重新训练 |
| 适用场景 | 知识频繁变化、需要引用来源 | 改变模型行为风格、领域适配 |
| 幻觉控制 | 较好（有检索文档做依据） | 一般（仍是参数记忆驱动） |
| 成本 | 推理成本（检索+生成） | 训练成本高，推理成本低 |
| 模型权重 | **不改变** | **改变** |
| 可追溯性 | 高（可以引用来源文档） | 低（知识融入权重，难以追溯） |

🕯️ **考试核心**：**RAG不更新模型权重**。这是最常考的区别点。RAG是"检索+生成"的流水线，LLM本身不变，变的是输入给LLM的上下文内容。

### Dense Retrieval vs Sparse Retrieval

| 维度 | Dense Retrieval | Sparse Retrieval（如BM25） |
|-|-|-|
| 原理 | 语义向量相似度 | 关键词匹配+词频统计 |
| 优势 | 理解语义，"意思相近"也能找到 | 精确匹配术语，速度快 |
| 劣势 | 可能遗漏精确术语 | 无法理解同义表达 |
| 适合场景 | 同义表达多的问答 | 术语精确的专业搜索 |

## 易错陷阱

1. **🚨 RAG不是微调**

   - RAG不更新模型权重，只是在推理时动态注入检索到的上下文
   - 考试中"RAG通过更新模型权重来融入新知识"的说法是**错的**
   - 微调改的是模型内部参数，RAG改的是模型的输入
2. **🚨 向量相似度高 ≠ 事实正确**

   - 语义相似不代表事实正确
   - 检索到的文档可能过时或本身有误
   - Faithfulness高只代表"忠于文档"，不保证文档是对的
3. **🚨 Embedding模型和LLM不是一回事**

   - Embedding Model专门做文本→向量的转换（如nv-embedqa）
   - LLM负责理解和生成文本（如Llama、GPT）
   - RAG中两者分工明确：Embedding管检索，LLM管生成
4. **🚨 RAG不能完全消除幻觉**

   - RAG显著降低幻觉，但不能根除
   - 如果检索到的上下文不完整或矛盾，LLM仍可能编造
   - 需要配合Guardrails和评估框架持续监控
5. **🚨 Chunking策略影响RAG效果**

   - 切得太小：上下文断裂，信息不完整
   - 切得太大：噪声太多，浪费Context Window
   - 需要根据文档类型和查询模式调整chunk size和overlap
6. **🚨 RAG评估不能只看最终答案**

   - 只看"答案对不对"无法定位问题出在哪
   - 答案错可能是因为检索没找到（检索层问题），也可能是LLM没用好找到的信息（生成层问题）
   - 必须分层评估，才能精准优化

## 练习题

### 题目1

一家公司需要让LLM回答关于公司内部政策的问题。政策文件每月更新一次。以下哪种方案最合适？

A. 每月用新政策数据微调LLM  
B. 使用RAG架构，将政策文件存入向量数据库，每月更新数据库  
C. 在Prompt中手动贴入所有政策文件  
D. 训练一个专门的公司政策模型

**答案：B**

**解析**：

- A：每月微调成本高、耗时长，而且微调不是让模型"记住"具体内容的好方式
- B：RAG是最佳方案——政策更新只需更新向量数据库，无需重训模型，且可以引用来源
- C：政策文件可能很长，超出Context Window，而且每月手动更新不现实
- D：从零训练成本极高，且更新时仍需重训

关键考点：RAG在知识频繁变化场景下的优势——**更新数据库即可，不改模型**。

### 题目2

在RAG系统中，用户问"如何配置NVIDIA Triton推理服务器"，检索返回了5个文档片段，其中3个是关于Triton的，2个是关于NVIDIA股票的。LLM基于这些文档生成了关于Triton配置的回答。以下哪个评估指标最低？

A. Context Recall  
B. Context Precision  
C. Faithfulness  
D. Answer Relevance

**答案：B**

**解析**：

- Context Precision = 检索结果中相关文档的比例 = 3/5 = 0.6，偏低
- Context Recall未知（取决于回答问题需要的信息是否都被检索到了）
- Faithfulness可能较高（因为LLM确实基于Triton文档回答了）
- Answer Relevance可能较高（回答确实在讲Triton配置）

两个关于股票的文档是噪声，拉低了Context Precision。优化方向：调小Top-K、提高相似度阈值、或使用Reranking过滤无关结果。

### 题目3

以下关于RAG的描述，哪个是正确的？

A. RAG通过微调模型来学习领域知识  
B. RAG中的向量数据库用于存储LLM的权重参数  
C. RAG在推理时动态检索相关文档并注入到LLM的上下文中  
D. RAG完全消除了LLM的幻觉问题

**答案：C**

**解析**：

- A错：RAG不微调模型，不更新权重
- B错：向量数据库存储的是文档的embedding向量，不是模型权重
- C正确：RAG的核心就是在推理时检索相关文档，拼接到Prompt中作为上下文
- D错：RAG显著降低幻觉，但不能完全消除（上下文不完整或矛盾时仍可能产生幻觉）
