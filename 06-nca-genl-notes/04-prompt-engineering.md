## 概念讲解

### 为什么 Prompt Engineering 重要？

你买了一把瑞士军刀，功能强大，但不会用就只是块铁。LLM 同理——同一个模型，好的 Prompt 和差的 Prompt 输出质量可能相差 30% 以上。作为 AI 产品经理，你的设计决策直接影响用户和模型交互的效果。

**Prompt Engineering = 学会提问的艺术 + 设计交互的逻辑**

---

### 四种核心 Prompt 范式

#### 1. Zero-shot Prompting（零样本）

**定义**：不给任何示例，直接让模型执行任务。

**例子**：

```text
把以下句子改写成正式语气：今天的天气真好啊

```

**适用场景**：任务简单明确，或模型本身对该任务已经很熟练。

#### 2. One-shot Prompting（一样本）

**定义**：给一个示例，让模型理解任务模式。

**例子**：

```text
把口语改成正式语：
示例：今天好热啊 → 今天气温较高
练习：这道菜真香

```

**适用场景**：任务边界需要示例来界定。

#### 3. Few-shot Prompting（少样本）⭐ 最常用

**定义**：给多个（通常 2-5 个）示例，帮助模型理解模式和边界。

**例子**：

```text
判断情感是正面还是负面：
文本：这部电影太精彩了！ → 正面
文本：服务态度很差，体验糟糕 → 负面
文本：味道还行，但是等太久 → ？

```

**关键点**：

- 示例要覆盖边界情况（正面、负面、中性）
- 示例之间要有区分度
- **不更新模型权重**——这只是输入上下文的一部分

**适用场景**：任务需要模式识别，Zero-shot 效果不好时。

---

### Chain-of-Thought（CoT）推理链 ⭐⭐ 重点

**定义**：让模型展示推理步骤，而非直接给答案。

**为什么有效**：模型在"展示推理"过程中，像人类一样逐步思考，减少跳跃性错误。

#### Zero-shot CoT

```text
请逐步思考：8 + 4 × 3 = ?

```

#### Few-shot CoT

```text
问题：小明有 5 个苹果，丢了 2 个，又买了 3 个，现在有几个？
解题步骤：
1. 先算丢了之后：5 - 2 = 3
2. 再算买了之后：3 + 3 = 6
答案：6

问题：小张有 10 元，花了 4 元，又收到 5 元，现在有多少钱？

```

**适用场景**：

- 数学推理
- 逻辑推理
- 多步骤问题

---

### Prompt 的三层结构

作为 PM，你设计的是**系统级交互**，需要理解这三层：

| 层级 | 英文 | 作用 | 示例 |
|-|-|-|-|
| **System Prompt** | 系统提示 | 定义 AI 的角色、行为规范、边界 | "你是一个专业的法律助手" |
| **User Prompt** | 用户提示 | 用户实际输入的内容 | "帮我写一份租房合同" |
| **Assistant Prompt** | 助手提示 | AI 的历史回复 | "好的，这是合同草稿..." |

**产品设计启示**：System Prompt 是你最能控制的层——定义好角色边界，用户体验会更稳定。

---

### 迭代式 Prompt 优化

好的 Prompt 不是一次写成的，是一个迭代过程：

```text
第1轮：测试 → 发现输出太泛
第2轮：分析 → 发现边界不清
第3轮：修改 → 添加约束和示例
第4轮：测试 → 验证效果
...循环...

```

**常见优化方向**：

- 增加示例（Few-shot）
- 添加输出格式约束（JSON、列表等）
- 拆分复杂任务为多步骤
- 添加"不要做什么"（Negative Prompt）

---

## 关键对比

### Zero-shot vs Few-shot

| 维度 | Zero-shot | Few-shot |
|-|-|-|
| 示例数量 | 0 | 2-5+ |
| 效果稳定性 | 较低 | 较高 |
| 成本（Token 消耗） | 低 | 高 |
| 适用场景 | 简单任务、模型熟悉的场景 | 边界复杂、需要模式学习 |

### CoT vs 直接回答

|  | 直接回答 | CoT |
|-|-|-|
| 输出长度 | 短 | 长 |
| 推理准确性 | 低（复杂问题） | 高 |
| Token 消耗 | 低 | 高 |
| 适用问题 | 事实类、简单推理 | 数学、多步逻辑 |

## 易错陷阱 ⚠️

1. **❌ Few-shot 不更新模型权重**

   - 这是最容易混淆的点：Few-shot 只是给输入加了示例，模型参数没有任何变化
   - 更新权重的是**微调（Fine-tuning）**，不是 Prompt Engineering
2. **❌ 示例越多越好？**

   - 超过 5-7 个示例，边际收益递减
   - 太多示例反而可能让模型困惑（尤其是示例本身有冲突时）
   - 质量 > 数量
3. **❌ System Prompt = 魔咒**

   - System Prompt 设定角色，但模型仍可能"出戏"
   - 需要配合具体的指令约束，不能只靠"你是 XXX"一句话
4. **❌ CoT 适合所有问题？**

   - 简单事实问题不需要 CoT（问"北京人口"，直接回答）
   - CoT 会让简单问题变复杂，还可能编造推理过程

## 练习题

### Q1：Few-shot Prompting 和模型微调的本质区别是什么？

A. Few-shot 使用更多示例B. Few-shot 不更新模型权重，微调会更新C. Few-shot 只能用于分类任务D. Few-shot 需要更多计算资源

**答案**：B**解析**：Few-shot 是在推理时通过输入中的示例引导模型输出，模型权重不变。微调是通过反向传播更新模型权重。A/C/D 都不准确描述本质区别。

---

### Q2：Chain-of-Thought (CoT) Prompting 最适合哪类问题？

A. "今天的日期是什么？"B. "把这段话翻译成英文"C. "计算 256 × 37 的结果"D. "推荐一部电影"

**答案**：C**解析**：CoT 适合需要**推理过程**的问题。A 是简单事实，B 是简单转换，D 是主观推荐——都不需要展示推理步骤。数学计算是最典型的 CoT 适用场景。

---

### Q3：以下哪个关于 System Prompt 的说法正确？

A. System Prompt 的内容会被模型"记住"超过对话轮次B. System Prompt 属于 User Prompt 的一部分C. System Prompt 定义 AI 的角色和行为边界D. System Prompt 的优先级低于用户输入

**答案**：C**解析**：System Prompt 用来定义 AI 的角色和约束，是产品设计中最重要的可控层。A 取决于产品实现（很多产品每次对话是独立的），B 错误（是独立层级），D 错误（System Prompt 优先级通常更高）。

---

### Q4（附加）：Prompt Engineering 属于机器学习的哪个范式？

A. 监督学习B. 无监督学习C. 强化学习D. **不是机器学习，是人机交互设计**

**答案**：D**解析**：这是概念辨析题。Prompt Engineering 本质上是"如何给模型有效输入"，属于人机交互设计范畴，不涉及模型参数更新。虽然它会影响模型输出质量，但不属于传统机器学习范式。
