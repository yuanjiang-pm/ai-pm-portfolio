# D3: LLM-as-Judge——让AI当裁判

## 📍 开篇引子

昨天你做完了错误分析，手里有一堆"失败模式"的清单。现在问题来了：**谁来打分？**

请人打分太贵、纯代码判断太蠢——于是LLM-as-Judge成了香饽饽。但我见过太多团队一头扎进去，结果发现：LLM当裁判，比让LLM干活还难伺候。

今天咱们聊聊怎么让AI当一个合格的裁判。

---

## 🎯 核心概念：LLM-as-Judge是什么？不是什么？

先厘清概念：**LLM-as-Judge就是用一个大模型来评估另一个系统（或同一个模型）的输出质量。**

它的优势很明显：

- 快：每秒能判几十条
- 便宜：API成本比人工低几个数量级
- 一致：不会因为心情不好影响判断
- 可规模化：想测多少测多少

但它的坑也很明显：

- 它可能会**偏心**自己的输出
- 它可能**过度宽容**或**过度严苛**
- 它的判断**未必准确**，尤其是需要专业知识的场景

### LLM-as-Judge不是什么？

**❌ 它不是灵丹妙药**"上了LLM-as-Judge，评估就自动化了"——想多了。Judge本身需要设计、测试、校准，这个工作量不一定比人工评估少。

**❌ 它不能替代所有评估**对于有明确对错标准的问题（比如代码能不能跑、JSON格式对不对），直接写assert，比用LLM判断快10倍且可靠10倍。

**❌ 它的结果不是"真相"**LLM的判断是一种"专家意见"，不是"客观事实"。你需要校准它，需要质疑它，需要用其他方式验证它。

### 什么场景适合LLM-as-Judge？

**适合的场景：**

- 需要"主观判断"的质量评估（相关性、完整性、可读性）
- 评估量级很大，人力不够
- 需要快速迭代，需要即时反馈
- 同一标准的重复性评估

**不太适合的场景：**

- 需要专业知识或实操经验（比如医疗、法律建议是否合规）
- 需要最新信息（LLM知识有截止日期）
- 需要避免模型偏见的情况

## 🛠️ 实操方法：设计一个合格的LLM裁判

### 第一步：构建Prompt四要素

一个合格的Judge Prompt，必须包含这四个要素：

**1. 设定角色**让LLM知道它是"什么身份"在评判。

```Python
JUDGE_PROMPT = """
你是一位经验丰富的AI产品评审专家。你的任务是根据用户需求，评估AI助手的回答质量。
"""

```

**2. 提供上下文**告诉LLM需要了解的背景信息。

```Python
JUDGE_PROMPT = """
## 评估背景
- 用户需求：{user_query}
- 实际回答：{response}
- 参考信息：{context}
"""

```

**3. 阐明目标**明确"好"的标准是什么。

```Python
JUDGE_PROMPT = """
## 评估标准
你的评估应关注以下几点：
1. 回答是否解决了用户的问题
2. 信息是否准确、可信
3. 表达是否清晰、有条理
"""

```

**4. 定义术语和标签**让输出格式可预期、可解析。

```Python
JUDGE_PROMPT = """
## 输出格式
请按以下格式返回评估结果：

评分：pass / fail
理由：[用一句话说明判断理由]
问题：[如果fail，指出具体问题是什么]

"""

```

### 第二步：选择判断方式——二元判断还是Likert量表？

**强烈推荐二元判断（pass/fail），尽量避免1-5分制。**

为什么？

| Likert量表(1-5分) | 二元判断(pass/fail) |
|-|-|
| 边界模糊：3分和4分差在哪？ | 边界清晰：要么达标，要么不达标 |
| 人与人之间不一致性高 | 一致性更高 |
| 聚合后的"平均分"意义有限 | 统计"通过率"直观易懂 |
| 容易出现"中庸陷阱" | 逼迫做出明确判断 |

但二元判断也有个问题：**如果你的业务需要区分不同"质量档位"怎么办？**

我的建议是：**定义多个二元Eval，每个Eval测一个维度**。

```Python
# 方案：多个二元Eval组合
EVALS = {
    "relevance": "回答是否与用户问题相关",
    "accuracy": "回答中的信息是否准确",
    "completeness": "回答是否完整覆盖了问题要点",
    "clarity": "回答是否表达清晰",
}

def evaluate_response(query: str, response: str, context: str):
    results = {}
    for dimension, description in EVALS.items():
        prompt = f"""
你是一位评审专家。
问题：{query}
回答：{response}

请判断：{description}
输出：pass 或 fail
"""
        result = call_llm(prompt)
        results[dimension] = result
    
    return results

```

### 第三步：Critique Shadowing——让专家教你写Prompt

这是我自己用过最有效的方法，原理很简单：

1. 找3-5个你领域的**真实判断案例**（已经有人做过判断的）
2. 让领域专家（可以是你的PM同事、业务专家）先做判断，并写出理由
3. 用专家的判断来**反推Prompt该怎么写**

具体操作：

```Python
# 第一步：收集专家判断案例
EXPERT_CASES = [
    {
        "query": "你们最贵的套餐是哪个？",
        "response": "我们有入门版299/月、标准版599/月、高端版999/月。",
        "expert_verdict": "pass",
        "expert_reasoning": "用户问最贵的，给出了最贵的（999/月），同时提供了完整的价格参考，信息充分。"
    },
    {
        "query": "你们支持退货吗？",
        "response": "支持的，7天内可以申请。",
        "expert_verdict": "fail",
        "expert_reasoning": "用户问'支持退货吗'，需要具体退货政策，回复应该包含退货条件、流程等完整信息，当前回复信息不完整。"
    },
    # ... 更多案例
]

# 第二步：从专家理由中提取Prompt关键词
# 案例1关键词：明确给出具体信息、提供上下文
# 案例2关键词：信息不完整、缺少具体政策细节

# 第三步：写Prompt
JUDGE_PROMPT = """
你是一位AI产品评审专家。

判断标准：
- 【信息充分】对于价格/产品类问题，需要给出具体数值
- 【政策完整】对于退货/规则类问题，需要包含完整条件和限制

判断：pass 或 fail
理由：（用一句话说明）
"""

```

### 第四步：Few-shot——给模型看例子

如果你的场景比较复杂，单纯描述标准不够，可以给几个例子：

```Python
FEWSHOT_JUDGE_PROMPT = """
你是一位AI产品评审专家。

## 判断标准
根据回答是否满足用户需求，判断pass或fail。

## 示例

示例1:
用户: "帮我查一下iPhone 15的价格"
回答: "iPhone 15 128GB版本售价5999元。"
判断: pass

示例2:
用户: "帮我查一下iPhone 15的价格"
回答: "我帮你查一下相关信息。"
判断: fail
理由: 用户需要具体价格信息，但回答没有给出任何价格数据。

## 待评估

用户: "{query}"
回答: "{response}"
判断: pass 或 fail
理由:
"""

```

## ⚠️ 避坑指南

**❌ 反模式1：追求泛化指标**"请评估回答是否有幻觉"——这是泛化指标，你永远不知道LLM怎么定义"幻觉"。改成"请检查回答中的事实是否与上下文一致"，具体多了。

**❌ 反模式2：标准模糊**"请评估回答质量"——什么叫质量？每个人都有一套自己的标准。你必须把标准拆解到**具体、可观察、行为化**的层面。

**❌ 反模式3：迷信ROUGE/BERTScore**这些指标测的是"文本相似度"，不是"质量"。两篇都是垃圾，但用词差不多，相似度也高。别用它们来判断主观质量。
