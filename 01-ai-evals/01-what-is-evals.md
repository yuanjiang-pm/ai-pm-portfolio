# D1: Evals是什么——从"感觉不错"到"数据说话"

## 📍 开篇引子

你有没有过这种经历：产品上线前，你满怀信心地点了几下，说了句"感觉还不错"，然后就拍板发布了。结果用户一顿吐槽，你才意识到——"感觉"这东西，骗起人来比LLM还狠。

上周就有个真实的例子。一个做电商客服AI的团队，功能上线前测试了一周，全组都说"挺顺的"。结果第一天高峰时段，用户问"我的订单什么时候到"，AI哗哗给了一堆物流术语，用户直接炸了——人家就想要个准话，你给一堆专业词汇算怎么回事？但你说他们测试有问题吗？还真没有：系统没崩、接口没报错、JSON格式正确、连日志都是绿的。传统测试一个不落，全过了。

问题在哪？问题在于**他们测的是"火车会不会脱轨"，但用户关心的是"司机会不会开车"**。

今天咱们聊的，就是怎么让AI系统的质量评估，从玄学变成科学——怎么不仅知道AI"能不能做到"，还能知道它"做得好不好"。

## 🎯 核心概念：Evals不是测试，是衡量AI价值的尺子

### 测试 vs Evals：这不是文字游戏

先来一个灵魂拷问：**测试和Evals，到底有什么区别？**

传统软件测试像什么呢？像检查火车会不会脱轨。铁轨有没有断、车轮有没有裂、刹车灵不灵——这些都是**确定性的边界检查**，对就是对，错就是错。你写一个`assert response.status_code == 200`，它要么绿要么红，没有中间地带。

但AI系统不一样。一个聊天机器人回复得好不好、一篇摘要有没有抓住重点、一段翻译有没有"内味儿"——这些东西没有标准答案。你没法写`assert response == "正确答案"`，因为正确答案根本不存在。

**Evals（评估）就是干这个的：它是一套衡量AI系统"效果"的方法论**，专门解决"没有标准答案"这个问题。

类比一下：**传统测试是安检，Evals是驾照考试**。安检检查你的车有没有故障，驾照考试评估你能不能安全驾驶。前者有明确的通过/失败标准，后者需要你实际表现来判断。

#### 一个真实的"测试全过但Eval挂掉"的例子

让我给你拆解一下开头那个电商客服的案例，看清楚"测试"和"Evals"到底在管什么：

**传统测试能覆盖的**（全部通过）：

- ✅ 订单查询API返回200
- ✅ 返回的JSON格式正确，包含order_id、status、estimated_time字段
- ✅ 响应时间在500ms以内
- ✅ 没有触发安全词/敏感词过滤
- ✅ 极端情况（订单不存在）返回了错误码

**Eval才能发现的**（实际暴露的问题）：

- ❌ 用户问"什么时候到"，系统返回一堆物流状态码，用户根本看不懂
- ❌ 用户同时问了两个问题（订单+售后），系统只回答了一个
- ❌ 用户表达焦虑时（"都三天了怎么还没到"），系统语气冷漠像机器人
- ❌ 用户追问细节（"是顺丰还是圆通"），系统答不上来开始编造
- ❌ 非标准问法（"我的件儿到哪了"）直接识别失败

你看，测试告诉你"系统在工作"，Eval告诉你"用户在满意"——这两件事可以完全独立。

**判断标准对照表**：

| 维度 | 传统测试 | Evals |
|-|-|-|
| **目标** | 功能是否正常运行 | 效果是否令人满意 |
| **判断依据** | 确定性规则（对/错） | 模糊标准（好/坏/还行） |
| **覆盖范围** | 已知边界条件 | 开放域表现 |
| **失败表现** | 报错/崩溃/返回错误 | 结果"能用但不够好" |
| **迭代信号** | 修复bug | 改进体验 |

### 三种武器：AI评估的三种方法

在实际工作中，你主要会用到三种评估方法。它们不是三选一，而是组合使用——就像木匠的锯子、锤子和钉子，各有各的用武之地。

#### 武器1：人工Evals（Human Eval）—— 金标准，但贵

**本质**：找真人来打分。

这是最可靠的评估方式，因为最终用户也是真人。任何自动评估方法，最终都要用人工评估来校准。

**典型工作流**：

```text
收集测试用例 → 分发给标注人员 → 制定评分标准（如1-5分） → 多人独立打分 → 统计结果

```

**适用场景**：

- 发布前的最终验收，特别是高风险场景（医疗、金融、法律建议）
- 探索性测试：你不确定问题在哪，需要人的直觉去发现
- 主观体验类评估：语气、风格、情感共鸣这些AI很难判断的东西
- 校准其他Eval：先用人工评一批，再用这些数据验证你的LLM-as-Judge准不准

**成本和现实**：

- 时间成本：一条输出人工评估平均5-10分钟（含阅读上下文和打分）
- 金钱成本：外包标注0.5-2元/条，内部员工做更贵（还要算机会成本）
- 规模化瓶颈：100条数据已经很多了，1000条基本是极限

**团队分配建议**：

- 核心路径（用户最高频使用的功能）：100%人工验证
- 重要但低频的功能：人工验证前50条+自动覆盖后续
- 实验性功能/灰度发布：抽样10-20%人工验证

#### 武器2：代码Evals（Code-based Eval）—— 快准狠，但有边界

**本质**：用规则或脚本自动检查对错。

这是最容易被低估的武器。很多团队觉得"AI的输出没有标准答案，怎么写代码测"，其实只要稍微转换思路，能测的东西比你想象的多。

**适用场景**：

- 格式验证：输出是否是有效JSON/HTML/代码块
- 关键词/实体检查：是否包含必要信息（如价格、日期、人物）
- 边界条件：空输入、超长输入、特殊字符
- 简单二分类：是否触发了安全过滤、是否调用了正确工具

**典型工作流**：

```Python
# 典型的代码Eval流程
def eval_response_format(response: str) -> dict:
    """检查响应格式是否符合要求"""
    result = {"passed": True, "errors": []}
    
    # 检查是否是JSON格式
    try:
        json.loads(response)
    except:
        result["passed"] = False
        result["errors"].append("不是有效JSON")
    
    # 检查必要字段
    required_fields = ["answer", "confidence"]
    for field in required_fields:
        if field not in response:
            result["passed"] = False
            result["errors"].append(f"缺少字段: {field}")
    
    return result

```

**成本对比**：

| 方式 | 单次成本 | 1000条成本 | 速度 |
|-|-|-|-|
| 人工评估 | 2元 | 2000元 | 慢（天级） |
| 代码Eval | 0.01元 | 10元 | 快（分钟级） |
| LLM-as-Judge | 0.1元 | 100元 | 中（小时级） |

**团队分配建议**：

- 代码Eval应该覆盖80%以上的常规检查
- 每发现一个问题模式，就写一个代码Eval把它自动化
- 这是你迭代速度的保障

#### 武器3：LLM-as-Judge—— 规模化，但需要精心调教

**本质**：让另一个AI（通常比你的模型更强）来评估你的AI输出。

这是近年来最流行的评估方法，因为它的成本介于人工和代码之间，但可以处理更复杂的"主观判断"。

**适用场景**：

- 文本质量评估：回复是否相关、完整、有帮助
- 对比评估：方案A和方案B哪个更好
- 开放式生成质量：摘要是否抓住了重点、翻译是否流畅
- 作为"虚拟标注员"：生成大量带标签的测试数据

**典型prompt模板**：

```Python
JUDGE_PROMPT = """
你是一个专业的AI助手质量评估员。请评估以下AI助手的回复质量。

【用户问题】
{query}

【AI回复】
{response}

【评估维度】
1. 相关性：回复是否针对用户问题？
2. 准确性：回复内容是否正确可靠？
3. 完整性：是否完整回答了用户的问题？
4. 清晰度：表达是否清晰易懂？

请给出1-5分的评价，并简要说明理由。

评分格式：
分数: X
理由: ...
"""

```

**避坑提醒**：

- LLM-as-Judge也有偏见（偏好长回复、偏好特定风格）
- 需要用人工标注数据来校准和验证
- 关键场景不能完全依赖它

**团队分配建议**：

- 用于快速迭代和大规模回归测试
- 人工评估作为兜底，特别是分数边界附近的case
- 定期抽样人工复核Judge的判断是否靠谱

#### 三种武器组合策略

实际项目中，成熟的团队通常这样分配：

```text
日常迭代（快速反馈循环）
├── 代码Eval：自动检查，CI/CD集成，失败就阻塞
├── LLM-as-Judge：每晚批量跑，覆盖全量case
└── 人工抽样：每天5-10条，侧重高风险场景

重大版本发布
├── 人工全面验收：核心路径100%覆盖
├── LLM-as-Judge对比：新旧版本差异
└── 代码Eval回归：确保没有引入新bug

```

### 产品Evals vs 基准测试：你测的到底是谁的成绩？

这里有个新人常踩的坑：把"基准测试"当成"产品Evals"。

**基准测试（Benchmark）** 是学术界发明的，比如MMLU考你的模型在选择题上能不能吊打人类、HumanEval考你代码写得好不好。它测的是**模型本身的能力**，用的是别人准备好的题库。

**产品Evals（Product Evals）** 测的是**你的系统在你自己的任务上的表现**。你用的是什么prompt、接了哪些工具、走了什么RAG流程——这些加起来才是你的产品。别人给你一个"模型准确率80%"，对你的产品毫无意义，你得在自己的场景上测。

打个比方：基准测试是体育总局的统一体能测试，产品Evals是你公司定制的岗位技能考核。你招的是销售，候选人体能测试满分，但你问TA怎么谈客户，TA支支吾吾，你说谁的锅？

#### 为什么MMLU分数对产品经理没用？一个真实的"高分低能"场景

让我给你讲个真实发生过的故事（改编自真实案例）：

某教育科技公司要上线一个AI作文批改功能，团队在选型时做了充分调研：

- GPT-4 MMLU得分89%，Claude 87%，国内某模型82%
- 价格对比：国内模型只有GPT-4的1/5
- 老板拍板："就选这个，便宜又好用！"

上线第一周，用户投诉率30%。什么问题？

**基准测试测的是**：选择题——"这句话有语法错误吗？"→ A.有 B.没有**产品需要的是**：实际批改——"请指出这篇文章的问题，并给出改进建议"

国内模型在选择题上82%，看起来不错，但它在长文分析、上下文一致性、写作建议质量上表现远不如GPT-4。而这些才是产品真正需要的。

后来团队用产品Evals重新测试：

- **同等成本下**，GPT-4的作文批改满意度85%，国内模型只有52%
- **扣掉成本差异**后，GPT-4的性价比反而更高

**教训**：基准测试是参考，但你的产品Evals才是决策依据。

## 🧠 Eval设计思维：从业务目标倒推评估维度

这一节是新加的，因为很多团队做Evals容易犯一个错误：**从技术指标出发，而不是从业务目标出发**。

### 常见的错误思路

❌ "我们要测RAG系统的faithfulness"❌ "我们要把MMLU、HellaSwag这些基准都跑一遍"❌ "我们加个BLEU分数来衡量翻译质量"

这些思路有什么问题？它们都是从"有什么现成的指标"出发，而不是从"用户真正在乎什么"出发。

### 正确的思路：从业务目标倒推

正确的做法应该是：

**Step 1：明确业务目标**

> "用户使用这个功能的目的是什么？""什么样的输出能真正帮到用户？"

**Step 2：定义成功标准**

> "怎么才算'帮到'了？""用户满意的具体表现是什么？"

**Step 3：拆解评估维度**

> "影响'帮到'的因素有哪些？""哪些环节可能出问题？"

**Step 4：选择/设计评估方法**

> "这个维度用什么方法测最合适？人工、代码还是LLM-as-Judge？""需要多少数据才够？"

### 一个正向的例子

假设你在做一个法律咨询AI：

**❌ 错误思路**："我们测一下模型的MMLU和法律基准吧"→ 跑分90%，上线被用户骂死

**✅ 正确思路**：

1. **业务目标**：帮助普通用户理解法律问题，给出初步建议
2. **成功标准**：用户能看懂建议，知道下一步该做什么
3. **评估维度拆解**：

   - 准确性：法律条文引用是否正确？
   - 可理解性：普通人能否看懂？
   - 可操作性：用户知道下一步做什么吗？
   - 风险提示：是否说明了局限性？
4. **评估方法**：

   - 准确性 → 代码Eval（检查法条引用）
   - 可理解性 → LLM-as-Judge（让AI评估可读性）
   - 可操作性 → 人工Eval（这是核心体验）
   - 风险提示 → 代码Eval + 规则检查

**核心原则**：你的Eval矩阵应该反映用户的满意因素，而不是论文里的流行指标。

## 🛠️ 实操方法：最小可行评估

好了，道理懂了，怎么开始干？

我的建议是：**先跑起来，再迭代**。别一上来就搞大工程。

### 第一步：花30分钟做一次"快速Review"

找20-50条你系统最近的真实输出（或者测试环境的trace），找个安静的时间段，逐条过一遍。

这30分钟的收获，往往比你想的要多：

- 你会发现自己没意识到的失败模式
- 你会对"好输出"和"坏输出"有更具体的体感
- 你会发现一些连指标都抓不到的微妙问题

**注意**：这时候不要打分，不要写指标，就是纯粹地"感受"和"记录"。

#### 快速Review的具体操作流程

**抽样方法**：

- 如果你有1000+条trace，随机抽样50条
- 如果你只有几十条，全部看
- 优先覆盖：高频场景 + 低频但高风险场景 + 你直觉觉得可能有问题的地方

**Review时的记录模板**（不用写得很完整，几个关键词就行）：

```text
[Trace #23] 2024-01-15 14:32
用户问：帮我查一下我的订单状态，订单号是ORD-2024-00123
系统答：[链接] 查看订单详情
问题标记：⚠️ 
笔记：用户要的是一个状态，系统给了一个链接。链接在手机上不好用。

[Trace #24] 2024-01-15 14:45
用户问：这个手机壳是硅胶的吗？
系统答：是硅胶材质，材质为XX型号，符合国家标准...
问题标记：✅
笔记：回答太技术参数了，普通用户不需要这些。简洁直接更好。

[Trace #25] 2024-01-15 15:02
用户问：你们家支持退换货吗？
系统答：支持，7天内可申请退换货，具体流程请查看...
问题标记：✅
笔记：好。但用户可能还会问"怎么申请"，可以优化。

```

**Review时看什么维度**（第一遍不用全看，抓住2-3个你最有感觉的）：

| 维度 | 你在找什么 | 信号 |
|-|-|-|
| **相关性** | 回答和问题对得上吗？ | 答非所问、漏掉问题 |
| **准确性** | 内容是真的还是瞎编的？ | 数据错误、编造信息 |
| **完整性** | 问题被完整回答了吗？ | 只答一半、跳步 |
| **有用性** | 用户能直接用这个答案吗？ | 缺关键信息、不可操作 |
| **自然度** | 读起来像人话吗？ | 机械、重复、模板化 |

### 第二步：把感受写成Trace笔记

找一张纸或者一个文档，对着每条输出问自己：

- 这条输出解决用户问题了吗？
- 哪里让我觉得别扭？
- 如果我是用户，我会满意吗？

然后把关键词记下来。不用完整句子，几个词就行——"引用过时"、"语气太生硬"、"没理解意图"。

#### 更具体的Trace笔记模板

如果你的Review已经有一定规模，可以用这个更结构化的模板：

```Markdown
## 问题模式归类

### 模式1：信息缺失类
- 关键词：没回答、缺数据、不完整
- 出现次数：7次
- 典型case：Trace #12, #23, #41
- 猜测原因：RAG检索不到/模型不记得

### 模式2：格式/风格类  
- 关键词：太长、不易读、模板感
- 出现次数：5次
- 典型case：Trace #8, #19, #33
- 猜测原因：prompt没强调简洁

### 模式3：逻辑错误类
- 关键词：前后矛盾、自打脸、推导错
- 出现次数：3次
- 典型case：Trace #15, #28
- 猜测原因：上下文窗口问题/推理能力弱

## 下一步行动
1. 🔴 P0：修复逻辑错误（影响信任）
2. 🟡 P1：补充信息缺失（RAG优化）
3. 🟢 P2：优化格式风格（体验提升）

```

### 第三步：把你的发现变成代码

Review完之后，你会有一堆"感受"。现在把它们翻译成可执行的东西。

比如你发现"当用户问价格相关问题，系统经常不回答具体数字"，那就可以写一个**代码Eval**：

```Python
def eval_price_response(output: str, query: str) -> bool:
    """检查价格相关查询是否有具体数字回答"""
    if "价格" not in query and "多少钱" not in query:
        return True  # 不是价格问题，跳过
    
    # 检查输出中是否包含数字（价格标志）
    price_indicators = ["元", "块", "¥", "$", "美元", " RMB", "价格"]
    has_price = any(indicator in output for indicator in price_indicators)
    
    # 或者检查是否包含具体数字
    has_number = any(char.isdigit() for char in output)
    
    return has_price or has_number

# 使用方式
assert eval_price_response("这个产品299元", "这个多少钱") == True
assert eval_price_response("我帮你查一下", "这个多少钱") == False

```

这个assert就是你的第一个Eval。它不完美，但它是个**起点**。

import json
import re

def eval_json_format(output: str) -> dict:
    """
    检查输出是否是有效的JSON，且包含必要字段
    """
    result = {"passed": True, "errors": []}

            result["passed"] = False
            result["errors"].append(f"缺少必要字段: {field}")

# 测试

**示例3：安全/合规Eval**

```Python
import re

# 安全词列表（根据你的业务场景定义）
BLOCKED_PATTERNS = [
    r"联系方式.*\d{11}",  # 避免泄露用户手机号
    r"内部.*价格",
    r"竞品.*对比.*表格",
]

# 敏感内容检测
def eval_safety(output: str, context: dict) -> dict:
    """
    检查输出是否包含敏感内容
    """
    result = {"passed": True, "violations": []}
    
    # 检查是否包含禁止的模式
    for pattern in BLOCKED_PATTERNS:
        if re.search(pattern, output):
            result["passed"] = False
            result["violations"].append(f"触发了敏感模式: {pattern}")
    
    # 检查是否泄露用户隐私（简单示例）
    if context.get("contains_user_phone"):
        phone_pattern = r"1[3-9]\d{9}"
        if re.search(phone_pattern, output):
            result["passed"] = False
            result["violations"].append("检测到手机号泄露风险")
    
    return result

# 使用
result = eval_safety(
    "根据内部价格政策，这款产品原价599...",
    context={}
)
print(result)  # {'passed': False, 'violations': ['触发了敏感模式: 内部.*价格']}

```

**示例4：相关性Eval**

```Python
def eval_topic_relevance(query: str, output: str) -> bool:
    """
    简单的主题相关性检查
    如果输出中没有出现query中的核心名词，可能跑题了
    """
    # 提取query中的中文词（简单实现）
    query_words = set(re.findall(r'[\u4e00-\u9fa5]+', query))
    
    # 过滤停用词
    stopwords = {"的", "了", "是", "在", "我", "有", "和", "就", "不", "人", "都", "一", "一个", "上", "也", "很", "到", "说", "要", "去", "你", "会", "着", "没有", "看", "好", "自己", "这"}
    query_keywords = query_words - stopwords
    
    # 检查输出中包含多少关键词
    if len(query_keywords) == 0:
        return True  # 没有关键词，跳过
    
    output_words = set(re.findall(r'[\u4e00-\u9fa5]+', output))
    overlap = query_keywords & output_words
    
    # 如果超过一半的关键词没出现，可能跑题了
    return len(overlap) >= len(query_keywords) * 0.3

# 测试
print(eval_topic_relevance("这个手机支持5G吗", "这款手机支持5G网络制式"))  # True
print(eval_topic_relevance("苹果价格多少", "这款安卓手机性价比很高..."))  # False

```

### 第四步：记录你的Trace

Trace是什么？**Trace是完整的行为记录**——用户说了什么、模型返回了什么、中间调用了哪些工具、检索了什么数据、每一步的输入输出是什么。

你不需要一开始就用什么高大上的工具，简单的JSON日志就行：

```Python
import json
from datetime import datetime

def log_trace(query: str, response: str, metadata: dict):
    """记录一次完整的交互"""
    trace = {
        "timestamp": datetime.now().isoformat(),
        "query": query,
        "response": response,
        "metadata": metadata,
        # 你可以根据需要添加更多字段
        "retrieved_docs": metadata.get("retrieved_docs", []),
        "tools_called": metadata.get("tools_called", []),
    }
    
    # 写入日志文件
    with open("traces.jsonl", "a") as f:
        f.write(json.dumps(trace, ensure_ascii=False) + "\n")
    
    return trace

```

#### Trace架构设计指南

有了Trace，你才有可能做真正的分析。但不是所有字段都同等重要，下面是一个推荐的Trace设计：

**必记字段**（没有这些Trace基本没用）：

```Python
{
    "trace_id": "uuid",              # 唯一标识，方便关联
    "timestamp": "ISO时间",           # 时间戳，用于分析趋势
    "query": "用户输入",              # 原始输入
    "response": "模型输出",           # 原始输出
    "model": "gpt-4-turbo",          # 使用的模型，便于对比
}

```

**强烈推荐**（支持深度分析）：

```Python
{
    "user_id": "用户ID",             # 用户维度分析
    "session_id": "会话ID",          # 关联多轮对话
    "round": 1,                       # 第几轮对话
    "latency_ms": 1234,              # 响应延迟ms
    "token_usage": {"prompt": 500, "completion": 200},  # token消耗
    "status": "success",             # success/error/partial
}

```

**可选字段**（根据你的系统复杂度添加）：

```Python
{
    "retrieved_docs": [...],         # RAG检索到的文档
    "tools_called": [...],           # 调用了哪些工具
    "prompt_version": "v2.1",       # prompt版本
    "context_window_utilization": 0.65,  # 上下文利用率
    "evaluation_result": {...},      # 如果你做了自动评估，结果放这里
}

```

**Trace设计的核心原则**：

1. **先记再说**：不确定要不要记的字段，先记上。空间便宜，数据宝贵。
2. **统一格式**：所有trace用同一个schema，便于批量分析
3. **留扩展字段**：预留`metadata`或`custom_fields`来应对未来需求

今天你Review的50条输出，就是你未来Evals体系的种子数据。Trace让你的"感觉"变成"证据"，让"我觉得"变成"数据显示"。

## ⚠️ 避坑指南

做Evals的过程中，新人最容易踩的坑有哪些？这里总结6条，每条都配上具体的反面案例，帮你绕开前人走过的弯路。

### ❌ 反模式1：上来就定指标

**典型表现**：

> "我们要建一套科学的评估体系！""计划：第一周完成指标设计，第二周搭Dashboard，第三周接入数据""结果：两周后Dashboard很漂亮，一条真实数据都没有"

**为什么是坑**：指标设计需要数据支撑。你没看过100条真实输出，你设计的指标大概率是"你觉得重要"而不是"用户在乎的"。

**正确姿势**：先手动Review 50条，积累足够的感性认识，再开始设计指标和系统。

---

### ❌ 反模式2：只测"好消息"

**典型表现**：

> 测试集全是精心挑选的成功案例问AI的都是你提前想好答案的问题结果：AI在测试集上99%正确，上线用户一用40%出错

**为什么是坑**：你自己设计的测试集，天然带有你的偏见。AI在"舒适区"表现好不说明任何问题。

**正确姿势**：刻意找一些失败的、边缘的、你直觉觉得刁钻的case来测。找一些对AI有偏见的同事来"故意刁难"。

---

### ❌ 反模式3：把"能跑通"当"做对了"

**典型表现**：

```Python
# 代码检查：JSON格式正确 ✅
# 关键词存在 ✅  
# 没有报错 ✅
# 结论：这条回答正确！

```

**为什么是坑**：你测的是"行为"（系统有没有在做某事），不是"效果"（系统做的事对用户有没有用）。

**真实反例**：用户问："帮我取消订阅"系统答（JSON正确、没报错）：

```JSON
{"action": "cancel_subscription", "status": "success"}

```

但实际上订阅没取消成功！用户收到账单才发现。JSON格式正确≠问题解决了。

**正确姿势**：每个代码Eval都要追问：这测的是行为还是效果？如果只是行为，加上效果验证。

---

### ❌ 反模式4：指标单一化

**典型表现**：

> "我们用准确率作为唯一指标""准确率从80%提升到85%，上线！"结果：用户满意度没变，因为准确率没抓到真正重要的东西

**为什么是坑**：AI系统是多维度的。单一指标会激励"作弊"——模型优化了这个指标，但其他方面退化了你没看到。

**正确姿势**：建立指标矩阵，覆盖多个维度（准确性、有用性、响应速度、安全性等）。接受某些指标 trade-off。

---

### ❌ 反模式5：测试数据不更新

**典型表现**：

> "我们去年建的测试集，用了整整一年""准确率稳定在90%，很棒"结果：模型在测试集上过拟合了，在真实数据上表现差

**为什么是坑**：AI模型会"记住"测试集。当测试集长期不更新，模型可能不是在"解决问题"，而是在"做阅读理解题"。

**正确姿势**：

- 定期轮换测试集（比如每季度更新30%的测试case）
- 留一个holdout集，只在重要节点使用
- 监控真实分布和测试分布的差异

---

### ❌ 反模式6：忽视失败案例的分析

**典型表现**：

> "我们统计了失败率2%，比上周降低了0.5%""但是为什么失败？不知道""2%的失败case日志在哪？没人看"

**为什么是坑**：失败案例才是进步的源泉。2%的失败率如果来自100种不同原因，每个原因只有0.02%——你根本不知道怎么修。但如果这2%其实只来自5种模式，你就知道优先级了。

**正确姿势**：

- 每条失败的trace都要归类：是哪一种错误模式？
- 定期做"错误模式分析"，而不是只看数字
- 明天D2就会详细讲这个：）
