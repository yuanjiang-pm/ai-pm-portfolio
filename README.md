## 三个我真正想说的判断

这几条是我做完这 67 篇之后，真正沉淀下来的东西。它们都有对应的完整论证，可以点进去看。

### 一、RAG 评估必须"分家"，否则你永远不知道问题在哪一跳

RAG 是两阶段流水线：`Query → 检索 → Top-K 文档 → 生成 → 回答`。很多团队只看最终回答质量，这是瞎子摸象。

两个阶段目标不同，评估方法也必须不同：

| 阶段 | 评估什么 | 怎么评估 |
|---|---|---|
| 检索 | 文档相关性排序 | IR 指标（Recall@K、Precision@K、MRR） |
| 生成 | 回答质量 | LLM-as-Judge（Faithfulness、Completeness、Relevance） |

我在 [D6](01-ai-evals/06-rag-eval-and-tooling.md) 里给了一个 2×2 诊断矩阵，用它可以直接定位瓶颈：

| | 生成好 | 生成差 |
|---|---|---|
| **检索好** | 健康 | 问题在 Prompt / 模型 |
| **检索差** | 检索没找到，但模型"编"出来了 ← 最危险 | 两边都有问题 |

**最危险的是左下角**：检索其实没找到，但模型凭参数知识编出了一个看起来很像样的答案。这种 case 在只看最终答案的评估里会当成"通过"，上线后就是幻觉投诉。

→ 完整论证见 [01-ai-evals](01-ai-evals/)

### 二、Evals 的起点不是指标，是错误分析

花哨的评估指标，90% 是浪费时间。我见过太多团队花三个月定义评估体系，Dashboard 做得跟火箭控制台似的，上线后用户反馈跟没测过一样——因为他们从"有什么现成指标"出发，而不是从"系统到底怎么失败"出发。

正确路径是**两步编码法**（[D2](01-ai-evals/02-error-analysis.md)）：

1. **开放编码** —— 找 100 条真实 trace，逐条写观察笔记。不预判、不分类、不打分
2. **轴心编码** —— 把相似失败归类统计，直到"理论饱和"（连续 20–30 条没发现新模式）

还有一条原则叫**先找第一个失败**：失败经常是链式的，上游错了下游跟着崩。只看最终输出，你会把所有锅扣在生成模型头上——但 trace 可能显示，问题出在检索模块的 query 改写。

→ 完整论证见 [01-ai-evals](01-ai-evals/)

### 三、LLM-as-Judge 不是圣人，裁判也必须被考核

让 AI 当裁判是现在最流行的评估方法，但它有系统性偏见：**宽容偏见、严厉偏见、位置偏见、长度偏见**。不校准的裁判，数据参考价值有限——通过率从 30% 涨到 50%，你分不清是产品真的变好了，还是裁判这周心情好。

校准方法（[D4](01-ai-evals/04-judge-calibration.md)）：准备 50+ 条人工标注真值，跑裁判，算 **TPR**（识别好回答的能力）和 **TNR**（识别坏回答的能力）。

- "老好人"裁判：TPR 0.95 / TNR 0.4 → 把所有坏回答都放过
- "杠精"裁判：TPR 低 / TNR 高 → 反过来

拿到 TPR/TNR 之后，还能反过来修正原始通过率，估算真实水平。

三类评估方式的成本结构（[D1](01-ai-evals/01-what-is-evals.md)）：

| 方式 | 单次成本 | 1000 条成本 | 速度 |
|---|---:|---:|---|
| 人工评估 | 2 元 | 2,000 元 | 天级 |
| LLM-as-Judge | 0.1 元 | 100 元 | 小时级 |
| 代码 Eval | 0.01 元 | 10 元 | 分钟级 |

**结论不是"选一个"，而是分层组合**：代码 Eval 覆盖 80% 常规检查并接入 CI，LLM-as-Judge 每晚批量跑全量，人工每天抽 5–10 条做高风险兜底。

→ 完整论证见 [01-ai-evals](01-ai-evals/)
