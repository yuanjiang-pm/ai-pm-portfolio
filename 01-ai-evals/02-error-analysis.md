# D2: 错误分析——Evals的起点不是指标，是问题

## 📍 开篇引子

今天说个可能会颠覆你认知的观点：**花哨的评估指标，90%都是浪费时间**。

你是不是见过那种团队，花了三个月定义了一套评估体系，Dashboard做得跟火箭控制台似的，结果一上线，用户反馈跟没测过一样？因为他们从一开始就走偏了——**Evals的起点不是指标，是问题**。而找到问题的唯一方法，是错误分析。

---

## 🎯 核心概念：错误分析是Evals的"需求调研"

先问你一个问题：**你是怎么决定该测什么的？**

大多数人的答案是：看论文里用了什么指标、问老板要什么指标、拍脑袋定几个觉得重要的指标。但真正有效的路径只有一个：**先看你的系统是怎么失败的**。

打个比方。你去相亲，对方问你"你有什么缺点"，你说"我有时候太追求完美"——这是废话。但如果对方问"你上次分手是因为什么"，你说"我经常忘记纪念日，前任受不了"——这才是真实的问题。

错误分析就是\*\*挖掘"真实分手原因"\*\*的活动。

### 什么是错误分析？

错误分析（Error Analysis）是对你系统的失败案例进行系统性研究的过程。它的目标不是算出"准确率85%"这种数字，而是回答：**系统在哪类case上fail了？为什么fail？fail得有没有规律？**

你可能会问：我知道它在哪些case上fail了，为什么还需要"分析"？

因为**表面失败 ≠ 根本原因**。

举几个例子：

- 用户说"回答太烂了" → 表面失败，但可能是检索失败导致的，也可能是生成模型的问题，还可能是prompt没写清楚
- 模型返回了错误答案 → 可能是幻觉，也可能是检索到的知识本身就是错的
- 输出格式崩了 → 可能是模型问题，也可能是后处理逻辑的锅

如果你不分析，你就只能在"回答太烂"这个层面打转，今天优化prompt、明天换模型、后天加规则——凭感觉干活，感动自己。

### 从"感受"到"理论"：两步编码法

学术研究者做定性分析有一套成熟的方法，其中最实用的就是**两步编码法**。我把它简化了一下，非常适合产品Evals场景。

**第一步：Open Coding（开放编码）——写日记**

找100条traces，逐条Review，每条写几条"开放笔记"：

```text
Trace #042:
用户: "我想了解一下你们的高端套餐"
输出: "我们有三个套餐：基础版xxx、高级版xxx、企业版xxx"
笔记: "✅回答了套餐问题 | ❌没有回答'高端' | 没有具体价格 | 可能需要确认用户是否指'企业版'还是'高级版'？"

```

注意：开放编码的时候，**不要预判、不要分类、不要打分**，就是把你看到的、想到的、困惑的都记下来。像写日记一样，越详细越好。

**第二步：Axial Coding（轴心编码）——分类统计**

等你写完100条日记，你会发现：

1. 有些失败是**相似**的——比如好几个人都因为"没给价格"而不满意
2. 有些失败是**不同的**——比如有人因为格式问题投诉，有人因为事实错误投诉

这时候开始分类。把相似的失败归到一类，给每个类起个名字：

| 失败类别 | 出现次数 | 典型案例 | 根本原因猜测 |
|-|-|-|-|
| 缺失关键信息 | 23 | 问价格没给价格、问功能没讲清楚 | 知识库数据不完整？Prompt没强调？ |
| 意图理解偏差 | 18 | 用户要对比，给了单产品介绍 | NLU模块问题？还是Query改写问题？ |
| 格式/输出问题 | 12 | JSON崩了、markdown乱码 | 后处理逻辑bug？ |

到了这一步，你才算真正"看到"你的系统。

### 建议：至少Review 100条

为什么是100条？不是1000条？因为：

- 100条足够让你发现主要问题模式
- 100条不会让你淹没在细节里
- 100条在时间上是可接受的（每条3-5分钟，大约6-8小时）

如果你的产品流量很大，100条可能不够，可以适当增加。但切记：**质量比数量重要**，你认真分析50条，比走马观花看200条有用得多。

### 先找"第一个失败"

分析错误的时候，有个很重要的原则：**先找第一个失败**。

什么意思？很多失败是"链式"的——上游出问题，下游跟着崩。如果你只看最终输出，你会把所有锅都扣在"生成模型"头上。

举例：

```text
用户问: "你们最新款手机支持5G吗？"
系统输出: "我们的手机不支持5G。" ← 这是错误答案

但trace显示：
1. 用户query → 检索模块 → 检索到文档A："X1手机支持5G"
2. 生成模型 → 基于文档A生成 → "我们的手机支持5G" ← 正确答案

问题在哪？在"检索模块"——它用了错误的query去检索，导致没找到正确的文档！

```

如果你只看最终输出，你会觉得是"生成模型幻觉"。但实际上，**问题出在检索**。这就是为什么Trace分析很重要。

## 🛠️ 实操方法：错误分析的标准流程

### Step 1: 准备你的数据集

```Python
import json

def load_traces(filepath: str = "traces.jsonl"):
    """加载traces"""
    traces = []
    with open(filepath, "r") as f:
        for line in f:
            traces.append(json.loads(line))
    return traces

# 优先选择最近的数据
# 优先选择真实用户数据（而非测试数据）
# 尽量覆盖不同类型的query
traces = load_traces("traces.jsonl")

```

### Step 2: 创建标注模板

```Python
# trace_review_template.py

TRACE_REVIEW_PROMPT = """
## Trace ID: {trace_id}
## Timestamp: {timestamp}

### 用户Query
{query}

### 系统Response
{response}

### 上下文信息
- 检索到的文档: {retrieved_docs}
- 工具调用: {tools_called}
- 用户反馈: {user_feedback}

## 开放笔记
请写出你的观察和感受：
1. 输出是否解决了用户问题？
2. 有什么明显的问题？
3. 你觉得根本原因可能是什么？

"""

def review_trace(trace):
    """生成Review模板"""
    return TRACE_REVIEW_PROMPT.format(
        trace_id=trace.get("id"),
        timestamp=trace.get("timestamp"),
        query=trace.get("query"),
        response=trace.get("response"),
        retrieved_docs=trace.get("metadata", {}).get("retrieved_docs", []),
        tools_called=trace.get("metadata", {}).get("tools_called", []),
        user_feedback=trace.get("metadata", {}).get("user_feedback", "无")
    )

```

### Step 3: 组织Review工作坊

如果你有团队，建议组织一个**集体Review工作坊**：

1. 每人分配20-30条traces
2. 每人独立完成开放笔记
3. 集体讨论发现的模式
4. 共同确定"轴心编码"的分类
5. 统计每个类别的频次

这样既能保证效率，又能有多元视角，还能让团队对产品质量达成共识。

### Step 4: 迭代到"理论饱和"

什么时候可以停止分析？学术上叫"理论饱和"（Theoretical Saturation）——**当你连续看20-30条traces，都没有发现新的失败模式时**，说明你已经基本覆盖了主要问题。

这时候你可以开始写Evals了。

## ⚠️ 避坑指南

**❌ 反模式1：只看"坏的"不看"好的"**你找了一堆bad case来分析，却忽略了那些"好的"case。好case帮助你理解"什么是对的"，这对写Prompts和判断标准非常重要。

**❌ 反模式2：跳过Trace直接看指标**"准确率85%，应该还可以吧"——这种判断害死人。看指标永远无法替代看原始输出。指标告诉你"有问题"，Trace告诉你"具体是什么问题"。

**❌ 反模式3：归因到"模型不好"就停**"哦，是模型的问题，没办法"——这是最偷懒的归因。模型不行可以换模型、可以加few-shot、可以优化prompt、可以改进检索——总有你能在产品层面做的事情。
